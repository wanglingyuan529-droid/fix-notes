# 外网访问改为「代理优先」：直连 GitHub 只卡不报错，代理稳定 2–3 秒

> 日期：2026-10-22 · 环境：Arch Linux · niri + FlClash（127.0.0.1:7890）· 状态：✅ 已定

> 一句话结论：凡涉及访问外网的操作，一律优先使用本机正在运行的代理；仅当代理未开启、或已开启但仍无法访问目标时，才退回直连。

## 现象

同一条命令，两条链路的结果差了两个数量级：

- `git push` 直连 GitHub：**132 秒后**才报 `Failed to connect to github.com:443: Could not connect to server`
- 同一时刻改走本机代理：**立即成功**（`e1c8f3b..9188b3e  main -> main`）

`curl` 计时更清楚（`--max-time 10`，各跑 3 次）：

```
直连      : HTTP 200  10.001s   ← 撞上限，传输没跑完
直连      : HTTP 200  10.000s   ← 同上
直连      : HTTP 200  10.001s   ← 同上
代理 7890 : HTTP 200   1.951s
代理 7890 : HTTP 200   3.065s
代理 7890 : HTTP 200   2.462s
```

注意直连那三次**拿到了 200 响应头**——所以它看起来「能连」，实际是拿完头就卡住，超时退出码是 28。这种半死不活的状态最容易误判成「网络慢」，而不是「链路不可用」。

## 根因

不是代理有问题，是**默认路径的顺序选错了**。

本机到 `github.com:443` 的直连链路在当前网络下不可靠（能建连、有响应头，但整体传输经常卡死），代理链路正常。而此前沿用的约定是「先直连，失败再走代理」，于是每次外网操作都要先白等 1–2 分钟才切到代理。

算一笔账：一次 `git push` 直连失败要 132 秒，代理约 3 秒。顺序反过来，单次就省两分钟，而且不用盯着它失败。

## 修复：改为「代理优先」

> 凡涉及访问外网的操作，一律优先使用本机正在运行的代理；仅当代理未开启、或已开启但仍无法访问目标时，才退回直连。

三条执行要点：

**1. 先探测端口，不写死。** 代理软件不同端口会变（Clash 系默认 7890，但 FlClash / mihomo 等可改）：

```bash
ss -tlnp 2>/dev/null | grep -iE 'clash|mihomo|verge|v2ray|xray|sing-box' \
  | grep -oE '127\.0\.0\.1:[0-9]+' | head -1
# LISTEN ... 127.0.0.1:7890 ... users:(("FlClashCore",pid=1515,fd=6))
```

输出里能直接看到进程名，确认那是代理进程而不只是某个占端口的程序。

**2. 单条命令带代理，不写全局配置。**

```bash
git -c http.proxy=http://127.0.0.1:7890 -c https.proxy=http://127.0.0.1:7890 push origin main
```

需要给不认 `-c` 的工具（脚本、`vault.py` 之类内部调 git 的）用时，临时导出环境变量即可：

```bash
https_proxy=http://127.0.0.1:7890 http_proxy=http://127.0.0.1:7890 <命令>
```

**不要** `git config --global http.proxy`：代理一关，之后所有 git 操作都会卡在连不上的代理上，比现在更难查。

**3. 代理也不通时才直连。** 这一步要记下具体报错——那时问题在目标站或线路，而不在代理。

## 验证

- `git push` 走代理：`e1c8f3b..9188b3e  main -> main`，退出码 0
- `git ls-remote` 走代理能查到真实远程 HEAD（`9188b3e...refs/heads/main`）
- `gh api repos/.../commits/main` 复核提交信息与本地一致
- 上面的 curl 三轮对比：直连 3/3 撞上限，代理 3/3 正常完成

## 教训

**默认路径决定平均耗时。** 同一台机器上「代理优先」与「直连优先」不是快慢之争，是「3 秒」与「等 2 分钟后失败」。

判断「网络是不是代理的问题」，正确顺序是**先量化两条链路**（各跑几次 `curl -w '%{time_total}'`），而不是按「直连是默认」的习惯先试直连、把 132 秒的失败当成偶发。

另一个细节：`curl` 拿到 `HTTP 200` 不等于通。要同时看 `time_total` 和退出码——`--max-time` 触发时会超时退出，但先前收到的响应头已经把 `http_code` 写成 200 了。
