# pkill -f 把自己杀了：按命令行模式杀进程的自匹配陷阱

> 日期：2026-10-17 · 环境：Arch Linux · bash · 场景：系统升级中清理卡在慢速下载上的 yay 进程

## 现象

升级卡在慢速下载上，想清掉后台的 yay 进程，执行：

```bash
pkill -f 'yay -Syu'
```

结果**整条 bash 命令当场终止**：

```
[killed by signal: SIGTERM]
```

同一条命令里写在后面的清理、安装、验证**一行都没跑**，而且 pkill 本身没有任何输出，看起来像"莫名其妙断掉了"。

## 根因

`pkill -f` 匹配的是**完整命令行**，不只是进程名。

而执行这条命令的进程，其命令行本身就含有目标字符串：

```
bash -c "... pkill -f 'yay -Syu' ; echo ..." 
                    ^^^^^^^^^^^^ 自己的命令行里就有这个串
```

于是 pkill 把**自己和自己的父 shell 一起匹配上并杀掉**——典型的自匹配（self-match）。

## 排查

判据很特征化：

- 命令**没有跑完**，退出状态是 `SIGTERM`（或 137）
- 断点**恰好落在 pkill 那一行**：之前的输出正常，之后全无
- `pkill` 不打印它杀了谁，所以表象是"没有报错但没执行完"

看到这三个特征，先怀疑"谁发的信号"，而不是"命令写错了"。

## 步骤

### 方法 1：方括号技巧（最省事）

```bash
pkill -f '[y]ay -Syu'
```

`[y]ay` 作为正则会匹配 `yay`，但**执行者自己的命令行里字面写的是 `[y]ay`**，与 `yay` 不匹配 → 不会自杀。

### 方法 2：先取 PID 再 kill（最稳，推荐）

```bash
pgrep -af 'yay -Syu'        # 先看清楚要杀谁
kill <pid>                  # 用明确的 PID 动手
```

`pgrep` 默认排除自身，所以"先查再杀"是安全的。

### 方法 3：收窄匹配范围

- `pkill -x <name>` —— 精确匹配**进程名**（不含参数），不碰命令行
- 叠加 `-u <user>` / `--older <sec>` 等条件进一步收窄

## 坑

1. **同类陷阱不只在 pkill**：`pkill -f 'python train.py'`（脚本自身命令行含该串）、`killall bash`、`fuser -k` 都可能误伤调用者。
2. **`pkill -9` 更危险**：SIGKILL 下连 trap / 清理逻辑都不执行，临时资源（如 sudoers 规则、临时文件、防火墙规则）会**残留下来还没人知道**。
3. **别把 kill 和后续关键清理写在同一条命令里**：一旦自杀或误杀，清理逻辑全部不执行。本次差一点因此漏掉临时 sudoers 规则的撤销。

## 验证

```bash
pgrep -af '<pattern>'    # 目标已消失
echo $?                  # 1 = 没有匹配进程
ps -p $$                 # 当前 shell 还活着
```

## 教训

1. **按模式杀进程前，先确认这个模式不会匹配到自己的调用者**。判断方法很土但很有效：把自己的命令行原样读一遍，看那个串在不在里面。
2. **破坏性操作和"善后清理"必须分开执行**：凡是需要撤销的临时状态（NOPASSWD、临时文件、规则），清理步骤要是独立的下一步，不能和被中断的操作绑在同一条命令里。
3. **"没报错但没跑完"是一个独立的现象类别**：它通常意味着被信号打断了，而不是逻辑错误。往"谁发的信号"方向查，比复核代码更快。
